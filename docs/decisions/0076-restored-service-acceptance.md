# ADR-0076 恢复后的应用验收

六库与附件联合恢复通过后，在隔离目标上启动客服 JAR 和 AI HTTP 服务。两者使用恢复时新生成的受限数据库账号。客服附件使用目标 RustFS 的临时凭据。AI 启用受签名保护的 Runtime 查询，使用 mock 模型配置。启动不加载开发者的 `.env`。

验收通过客服 HTTP 接口比对聊天图片和公开头像的 SHA-256、MIME 类型与缓存响应。检查匿名、其他租户、同租户错误会话及误用公开头像入口。通过签名查询核对两个已恢复任务的来源事件、状态和计数，重复查询须保持结果一致。

在目标库临时重命名两个服务共同检查的 `kb_chunk.content`。探活应继续为 200，就绪探测和已授权业务读取应返回 503。用 `finally` 恢复列名，再用相同服务进程复查数据；恢复后重新校验实际结构及数据库行数。故障只在新建的目标库注入。

复现使用 JDK 25、已构建的客服 JAR、Docker 和本项目测试依赖，运行 `python scripts/test-database-restore.py --with-attachments --with-services`。结果在进程及容器清理后写入原演练报告。应用启动和故障恢复另计，延续上一批的数据恢复计时口径。回退时可省略 `--with-services` 继续运行联合恢复，应用代码和数据库迁移保持原版本。

该演练覆盖客服和 AI 的读取及结构故障恢复。生产切换、对象存储的运行时可用性门禁、在线备份与 WAL 仍需独立验证。
