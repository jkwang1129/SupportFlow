# SupportFlow 架构与核心链路

组成和启动顺序见[本地运行指南](local-development.md)。Java 服务负责会话、工单及租户等业务状态，Python 服务负责模型调用、知识库检索与回复建议，浏览器通过 HTTP 和 WebSocket 使用两者提供的能力。

| 组件 | 职责 |
| --- | --- |
| API 网关 | 路由 HTTP 请求、校验登录态、实施租户限流。 |
| 实时服务 | 管理坐席和访客长连接，处理消息确认、历史补拉和实时推送。 |
| Java 客服服务 | 保存会话与消息、发起 AI 回答、执行转人工，维护工单和 SLA。 |
| Python AI 服务 | 文档切分和向量化、租户知识库检索、意图识别和答复生成。 |
| PostgreSQL / RustFS | PostgreSQL 保存业务数据和向量；RustFS 保存上传文件。 |

## 从访客消息到工单

1. 访客通过网站渠道创建会话，再携带会话令牌连接实时服务。
2. 实时服务把消息交给客服服务。消息落库后返回带序号的确认，客户端可以用同一个消息编号重发。
3. 客服服务把最近的消息交给 Python AI 服务。检索时按租户筛选知识；资料不足或需要人工时，会返回对应建议。AI 服务调用失败时，Java 可以把会话转给人工。
4. Java 持久化机器人的回复或执行实际转接，并通过实时服务推送。坐席接管后可以从该会话创建工单，工单保留会话关联。

## 数据与可观测性

本地开发使用一个 PostgreSQL 实例初始化六个数据库，分别存放用户、租户、客服、计费、运营和 AI 数据。业务表按租户区分；知识库的向量与关键词检索都带租户条件，文档ID范围在关键词降级时保留。明确空文档列表会停止检索和生成，省略范围仍按当前租户查询。访客brain/chat固定只查询已发布且索引完成的文档；后台保留编写预览。这是查询时点的过滤，文档选择不授予访问权，完整ACL/版本/在途撤权后的最终核验仍待知识工具边界。模型调用可按请求 ID 查看耗时、Token 和成败，客服与知识问答可以返回编排步骤。

业务状态和会话上下文已入库。默认LangGraph每轮从入口执行，未接原生节点checkpointer。独立的显式Runtime已有Run/Step、租约与fence、共享执行预算，以及模型/只读/报告正文原子Checkpoint；真实Worker进程退出后的接管已验收。两条入口尚未自动切换，HITL审批尚未实现。知识问答引用检查仍只核来源编号，无法自动判断每个结论是否有事实支持。

知识问答在一次改写后仍低于召回阈值时，确定性停止生成并提示澄清或联系人工；该策略在 LangGraph 和线性实现中一致。节点步骤关联现有请求 ID、序号和拒答原因，但还不是持久化的 Agent Run/Step Trace。

会话消息写入通过数据库行锁重新判重后分配序号，坐席认领使用原子条件更新。旧机器人轮次使用保留等待者引用的进程内锁。新Runtime的多Worker通过数据库领取/心跳/过期接管和同会话顺序协调；来源与工单查询当前核权，有界模型Loop产出固定事实报告，再经短期写许可提交业务消息和原子回执。显式回复核销只能确认既成提交；取消任务保持失败，无回执的未知写继续阻断，不盲重发。数据库提交不等于外部渠道送达。可信自动登记/路由、知识工具、创建工单及完整成本治理仍待接入，默认开关保持关闭。能力范围、测试模式及实际结果见 [工程计划](agent-engineering-plan.md) 和 [可靠性验收](reliability-verification.md)。
